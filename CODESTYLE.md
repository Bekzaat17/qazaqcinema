# CODESTYLE.md — как писать код в этом проекте

Правила для всех, кто правит этот репозиторий, включая агентов. Читать ПЕРЕД первой правкой,
вместе с [CLAUDE.md](CLAUDE.md) (что уже решено и почему).

Смысл документа один: чтобы добавление новой фичи было строкой данных или новым классом, а не
правкой десяти существующих мест. Всё ниже уже соблюдается в коде — это описание проекта, а не
пожелания. Часть проверяется линтером (помечено 🤖), остальное — на совести автора правки.

Правило конфликтует с реальностью? Значит либо код надо привести к правилу, либо правило
изменить здесь осознанно и одним коммитом. Молча писать иначе — нельзя: именно так появляются
костыли.

---

## 1. Слои и направление зависимостей 🤖

Главное правило архитектуры: **зависимости смотрят внутрь**.

```
bot/ api/  →  application/services  →  application/ports  ←  infrastructure/
                        ↓                      ↓                    ↓
                     domain/  ← ничего не импортирует, кроме себя
```

- **`domain/`** — ни одного внешнего импорта. Чистые функции, `dataclass`, `StrEnum`, правила.
  Тестируется без БД, Telegram и времени.
- **`application/ports/`** — только `Protocol` и `dataclass` для передачи данных. Порт мелкий и
  по одному концерну (ISP): `MovieRepository` ≠ `UserRepository`, `Lock` ≠ `RateLimiter`.
- **`application/services/`** — use-cases. Импортируют порты и домен, **никогда** `infrastructure`.
- **`infrastructure/`** — единственное место, где живут aiogram, SQLAlchemy, Redis, Pillow, PyYAML.
  Один адаптер = одна реализация порта.
- **`bot/`, `api/`** — тонкие входы: разобрать апдейт или запрос → позвать сервис → отдать ответ.
  Бизнес-правил в хендлере и роутере нет. Ветвление по правилам продукта — в сервисе или домене.

🤖 Импорт фреймворка в `domain/` или `application/` — ошибка линта (`TID251`, список в
`pyproject.toml`). Проверено: подсунутый в домен `from aiogram.types import Message` падает.

**Новая внешняя штука** (сервис, библиотека, API) = порт в `application/ports/` + адаптер в
`infrastructure/` + провайдер в `infrastructure/di/providers.py`. Сборка руками в CLI или
хендлере — не вариант: конфиг читается в одном месте (composition root).

## 2. Имена 🤖

**Python** (`N` в ruff): `snake_case` — функции, переменные, модули; `PascalCase` — классы;
`UPPER_SNAKE` — константы модуля; ведущее `_` — приватное (в том числе константы и хелперы
модуля: `_ORDER`, `_movie_to_domain`).

- **Порт** — существительное по роли, без префикса: `MovieRepository`, `ChannelPublisher`,
  `CardRenderer`, `PosterStorage`.
- **Адаптер** — по технологии, префиксом: `PgUserRepository`, `AiogramNotifier`,
  `LocalPosterStorage`, `PillowCardRenderer`, `RedisSessionStore`. По имени видно, какая граница.
- **Исход операции** — `*Outcome` (`PlaybackOutcome`, `DeleteOutcome`), **ошибка** — `*Error`.
- Сервис — `*Service`, чистый расчёт — глагол (`compute_expiry`, `pick_daily_id`, `slot_for`).

**TypeScript** (`web/`): `camelCase` — переменные, функции, хуки (`useFavorites`); `PascalCase` —
компоненты и типы; файл компонента — `PascalCase.tsx`, хука — `useThing.ts`, утилиты — `thing.ts`.

**JSON API** — `snake_case` (его генерит pydantic: `hero_free_until`, `bot_started`). На фронте
поля читаются как есть, переименовывать на camelCase нельзя — контракт один.

**БД** — `snake_case`, таблицы во множественном числе (`movies`, `payment_requests`), время с
суффиксом `_at` (`created_at`, `bot_started_at`), счётчики `_count`, булевы `is_*`
(`is_active`). Миграции — `migrations/versions/yyyymmdd_<slug>.py`.

**Слаги** (категории, темы, тарифы, формы контента, коды ошибок API) — латиница `lower_snake`:
они попадают и в БД, и в URL, и во фронт. Ключи Redis — с namespace-префиксом, который навешивает
адаптер (`session:`, `catalog:`, `lock:`, `ratelimit:`, `broadcast:`).

## 3. Типы

- **mypy strict**, аннотации везде. `Any` — только на границе с библиотекой и с `cast` +
  комментарием, почему иначе нельзя.
- `from __future__ import annotations` в каждом модуле.
- Домен и передаваемые данные — `@dataclass(frozen=True, slots=True)`. Порты — `Protocol`.
  DTO наружу — pydantic-модель в `api/schemas/` (и там же защита: `telegram_file_id` не отдаём).
- **Замкнутое множество значений → `StrEnum`**, в БД хранится как VARCHAR (новое значение без
  миграции типа): `ContentKind`, `EventKind`, `UserStatus`, `PaymentMethod`, `PaymentStatus`.
  Строковых литералов по месту (`if kind == "quiz_open"`) быть не должно.
- **Открытый справочник → данные-словарь**, не enum: категории, тарифы, темы, сетка слотов.
  Добавление = одна строка, без кода и без миграции. Граница между «энум» и «справочник» —
  меняет ли значение ПОВЕДЕНИЕ (энум) или только подпись (справочник).
- **Несколько исходов операции → Enum исхода**, а не `bool`, `None` или строка.
  `PlaybackOutcome`, `DeleteOutcome` (три состояния вместо «получилось/нет»), `ModerationOutcome`.
  Вызывающий обязан разобрать все ветки, и новая ветка не притворяется старой.

## 4. Ошибки

- **Ожидаемая ветка — не исключение.** Нет доступа, повторный клик, флуд-лимит, пустой каталог —
  это `Outcome`-значение или `None`, а не `raise`. Исключение — для того, что сломалось.
- **Все свои исключения наследуют `AppError`** (`domain/errors.py`), а объявляются рядом с портом
  или сервисом, который их бросает. Так граница ловит «наше» одной строкой, а по имени класса
  видно, где искать причину.
- **Адаптер переводит чужие исключения в свои.** Наружу не летят `TelegramBadRequest`,
  `SQLAlchemyError`, `OSError`, `UnidentifiedImageError`. Классификация тоже в адаптере — он
  единственный, кто знает библиотеку (пример: `delete_message` → `DeleteOutcome`).
- **API**: `HTTPException(status, detail="snake_case_код")`. `detail` — стабильный код для фронта
  (`no_access`, `session_expired`, `try_later`), не текст для человека. Новый код добавляется
  вместе с обработкой на фронте.
- **`except Exception` — только там, где второстепенное не должно ронять главное**: журнал
  событий, уведомление админам, пост в канал, кэш. Обязательно с `logger.exception(...)`.
- **Fail-open — правило для адаптеров кэша, локов, лимитера, журнала и витрины**: Redis лёг →
  промах и работа дальше, а не 500. Основной путь (выдача видео, оплата) fail-open НЕ бывает.
- **Молча глушить нельзя.** `except: pass` без Outcome и без лога — прямой путь к «оно молчит и
  никто не знает» (так канал полгода не публиковал посты, а постеры уходили в никуда).
- Логи: `logger = logging.getLogger(__name__)`, `%`-формат (🤖 `LOG`, `G`), `print` запрещён (🤖 `T20`).

## 5. Время 🤖

- **Только aware `datetime`** (🤖 `DTZ`): наивный `datetime.now()` в UTC-контейнере рисует
  вчерашнюю дату до 05:00 по Казахстану.
- **`now` передаётся параметром** в сервисы и чистые функции (`has_active_access(now)`,
  `publish_daily_movie(now)`, `slot_for(now)`) — иначе поведение не проверить тестом.
- Внутри — UTC. **Местное время (Asia/Almaty) — только на границе с человеком**: расписание
  постов, часы отчётов, «сегодня бесплатно», ключ кэша главной.
- Часовой пояс один на проект (`domain/catalog/daily.TZ`). Второй не заводить.

## 6. Расширяемость: куда добавлять новое

| Что добавляем | Куда |
|---|---|
| Категория, тариф, тема, праздник | строка данных в справочнике |
| Способ оплаты | адаптер `PaymentProvider` + провайдер в DI |
| Форма поста в канал | рендерер + запись в `Registry` |
| Шаг визарда `/add` | строка в `_ORDER` / `_PROMPTS` / `EDIT_FIELDS` |
| Значимое событие | значение `EventKind` (VARCHAR, без миграции) |
| Ручка API | роутер + схема + метод сервиса |
| Поле снимка отчёта | колонка `daily_reports` + поле `DailyReport` (проценты не храним) |

**Признак костыля:** добавление требует правки существующего `if/elif`, копипасты соседнего
блока или второго флага в env рядом с первым. Тогда нужен реестр, словарь данных или адаптер —
это и есть OCP на практике.

## 7. Идемпотентность и внешние эффекты

- **Уникальность обеспечивает схема БД, а не проверка в коде**: `UNIQUE channel_post_log.slot_key`,
  `UNIQUE(post_id, user_id)` в ответах квиза, upsert по натуральному ключу (`slug`, `day`).
- Джобы планировщика — с `misfire_grace_time` + `coalesce`: рестарт внутри окна не должен
  ни потерять запуск, ни выполнить его дважды.
- Подписку выдаёт **только** `SubscriptionService.activate`. Платёжные хендлеры её не активируют.
- Повторный клик, misfire, вторая реплика не создают второго внешнего эффекта (поста, DM, гранта).

## 8. Конфигурация

- **Всё, что отличается между средами или может смениться** — в env через pydantic-settings:
  домен, `@`-имена, id каналов, часы расписаний, лимиты. В коде константами — только то, что
  от среды не зависит (размеры карточки, лимиты Telegram).
- **Проектных строк в домене быть не должно.** `@qazaqcinema_kz` на карточках жил константой,
  пока рядом лежала незадействованная переменная env — так делать нельзя.
- Секция конфига объявляет свой `env_prefix` и `env_file`; списки из env — `NoDecode` + валидатор.
- Новый ключ env → строка в `.env.example` и `.env.prod.example` с коротким комментарием.

## 9. Тесты

- **Правило поведения = тест.** Домен и рендереры — юнит без БД; сервисы — на фейках
  (`tests/fakes.py`); репозитории — интеграционные в БД с именем на `_test`.
- Имя теста называет ПРАВИЛО, а не метод:
  `test_ingest_without_notify_keeps_the_queue_silent_but_posts_to_channel`.
- Время в тестах фиксированное (`_NOW`), `datetime.now()` в тестах не вызываем.
- Регресс без теста не закрывается: сначала тест, который поймал бы поломку.
- Прогон перед коммитом: `ruff check app tests && mypy app && pytest -q`
  (на прод-сервере — в одноразовом контейнере, см. [CLAUDE.md](CLAUDE.md)).

## 10. Комментарии и докстринги

- Пишем **почему**, а не что: «что» читается из кода.
- **Никакой истории**: ни дат решений, ни «раньше было», ни номеров этапов. Правила — в CLAUDE.md,
  история — в git. Докстринг описывает текущее устройство, как будто оно всегда было таким.
- Внешние ограничения, на которые легко наступить, помечаем ⚠️ (Telegram не удаляет сообщения
  старше 48 ч; пост с inline-кнопками не попадает в группу обсуждений; `web_app`-кнопки в
  каналах не работают).
- Язык комментариев и докстрингов — русский. Тексты для пользователей — казахский.
- Строка ≤ 100 символов, импорты сортирует ruff.

## 11. Коммиты

- Один смысловой шаг = один коммит, прямо в `main` (без фича-веток). Сообщение объясняет
  **почему**, а не пересказывает диф.
- После каждого коммита проверки зелёные. Рефакторинг идёт этапами — очередь в
  [PLAN.md](PLAN.md) §3, каждый этап отдельным коммитом `Рефакторинг, этап N:`.
